# Открытые проекты GitHub: протокол Mercedes KWP2000, EGS52, CBF (сбор 2026-10-12)

Читали исходники (не README) трёх проектов, клон 2026-10-12:
- **ultimate-nag52-fw** (rnd-ash) — открытая прошивка блока АКПП 722.6, повторяет поведение штатного EGS51/52/53
  (чёрный ящик, без утёкших документов): https://github.com/rnd-ash/ultimate-nag52-fw
- **OpenVehicleDiag** (rnd-ash) — открытая диагностика Mercedes через J2534/SocketCAN, парсер CBF:
  https://github.com/rnd-ash/OpenVehicleDiag
- **CaesarSuite** (jglim) — разбор CBF-файлов Daimler (как c32s.dll), утилита кодирования Diogenes:
  https://github.com/jglim/CaesarSuite

Самих CBF (с адресами всех блоков W639) в репозиториях нет — они из Xentry/DAS и не публикуются.
Проекты дают протокол и форматы, а не таблицу блоков W639.

## 1. Наша АКПП на CAN 0x7E1/0x7E9 — это EGS (подтверждение)

- В прошивке ultimate-nag52 заданы «для совместимости с EGS52/53 их таймингами и CAN ID»:
  `KWP_ECU_RX_ID 0x07E1` (запрос тестера), `KWP_ECU_TX_ID 0x07E9` (ответ блока)
  (src/diag/kwp2000_defines.h). **Ровно наша пара.** Значит, отвечающий блок — EGS 722.6, а не что-то другое.
- Наш ответ `1A86` → `5A 86 00 34 46 41 …`. Формат 1A86 (OpenVehicleDiag read_ecu_identification.rs):
  байты 2..6 — номер детали в BCD, 7..8 — неделя/год железа, 9..10 — неделя/год ПО, 11 — поставщик,
  12..13 — вариант диагностики, 15..17 — дата производства. У нас видно начало номера: **A 003 446 41 ??**
  (последние 2 цифры обрезаны). Вывод: номера вида A 003 446 xx xx — это блоки EGS (не проверено по каталогу).
- Наш ответ `1A87` → `5A 87 03 08 03 53 …`. Формат 1A87: байт 2 — происхождение, 3 — поставщик,
  4..5 — вариант диагностики, 7..8 HW, 9..11 SW (BCD), 12+ — номер детали ASCII.
  У нас: происхождение 0x03, поставщик 0x08, **вариант диагностики 0x0353**. Diogenes именно по этим
  байтам (1A87 [4..5] или 1A86 [12..13]) выбирает вариант блока в CBF.
- Тайминги ISO-TP: ultimate-nag52 — BS 20, STmin 1 мс, таймаут 4500 мс, «ответ ожидается» (7F xx 78) каждые 500 мс.
  OpenVehicleDiag: «MB всегда использует block size 8», STmin по умолчанию 20 мс. Diogenes-пример:
  BS 8, STmin 0, P2 2100 мс, P2 после 7F 78 — 4500 мс.
  **Для нас:** настоящий блок ждёт от тестера Flow Control (30 xx xx) после первого кадра — наш клон его не шлёт,
  поэтому длинные ответы (1A86/1A87) обрезаны.

## 2. Mercedes KWP2000 поверх CAN (KW2C3PE) — команды

Из Diogenes (KW2C3PE.cs), ultimate-nag52 (kwp2000_defines.h), OpenVehicleDiag (kwp2000/mod.rs):
| Что | Запрос | Ответ | Примечание |
|---|---|---|---|
| Идентификация Daimler | `1A 86` | `5A 86 …` 16 байт | см. выше |
| Идентификация DCX/MMC | `1A 87` | `5A 87 …` 19–20 байт | |
| VIN исходный / текущий | `1A 88` / `1A 90` | 17 байт ASCII | наш EGS: `30 30 30 30…` («0000…», VIN не записан) |
| Вариант диагностики | `1A 89` | 4 байта | |
| Также | `1A 96 97 9A–9F` | калибровка, отпечатки ПО | |
| Ошибки | `18 02 FF 00` | `58 <кол-во> [hi lo статус]…` | 2-байтный HEX-код + статус; биты 5–6 хранение, бит 7 лампа |
| Tester present | `3E 01` | `7E 01` | `3E 02` — без ответа |
| Сессия | `10 81` штатная, `10 92` расширенная, `10 85` прошивка, `10 89` standby, `10 90` passive | `50 xx` | **по нашим правилам — только штатная** |
| Live data | `21 <LID>` | `61 <LID> …` | ReadDataByLocalIdentifier |

- EGS52 live data (ultimate-nag52 egs_emulation.h, «структуры для эмуляции EGS52 в DAS»), только чтение:
  - `21 30` — ГДТ: скольжение, давление, состояние; положение селектора; программа; распознанная/текущая/целевая
    передача; **температура ATF**; момент двигателя и на турбине; обороты выхода; флаги kickdown, соленоиды
    1-2/4-5, 2-3, 3-4, аварийный режим…
  - `21 31` — счётчики N2/N3, обороты входа и двигателя, скорости 4 колёс, скорость по осям.
  - `21 32` — педаль %, дельта оборотов переключений, уклон, ограничения диапазона.
  - `21 33` — давления SPC/MPC, токи соленоидов (цель/факт), ШИМ ГДТ, состояние клапанов.
  Раскладка байтов приведена в egs_emulation.h; она получена эмуляцией, в нашем блоке может отличаться.
- Коды ошибок EGS52 (ultimate-nag52 lib/dtcs/dtcs.h, «diagversion 51»): HEX-коды диапазонами
  P2000–P2012 внутренние, P2100–P210A соленоиды, P2200–P2226 датчики, P2300–P233B связь CAN,
  P2400–P2451 неверные данные CAN, P2500–P2564 передачи, P2600–P260F питание.
  **Нашего 0x1731 и 0xD40B в списке нет** — вывод: у нас другая версия диагностики EGS (Vito), или это не EGS52.
- OpenVehicleDiag выводит коды Mercedes KWP как **сырой HEX** (`%02X%02X`), без перевода в SAE.
  Вывод: наши «P1731» и «U140B» в Xentry могут выглядеть как `1731` и `D40B` — искать расшифровку по обоим видам.

## 3. K-line у Mercedes (OpenVehicleDiag CBFParser/src/main.rs)

- Интерфейсы CBF не-CAN (K-line) — **10400 бод всегда**, адрес блока — `CP_REQTARGETBYTE`, ответ —
  `CP_RESPONSEMASTER`, tester present — `CP_TESTERPRESENTADDRESS`, сегмент до 254 байт.
- Автор пишет: **«MB всегда использует 5-бод инициализацию с KWP2000 на K-line»**. При 5-бод init адрес блока
  передаётся в самой инициализации, поэтому на одной линии можно будить разные блоки.
  Вывод: для линий 8/9/11 нужен перебор адресов именно 5-бод init'ом (у ELM — `ATIIA` + `ATSP4`), а наш клон
  адрес игнорирует — см. 04_linii_8_9_11.md.

## 4. CAN: параметры и поиск блоков

- Пример параметров HSCAN_UDS_500 (Diogenes ECUConnection.cs): 500 кбит/с, функциональный запрос `0x441`,
  физический `0x7E0`/`0x7E8`. Имена параметров CBF: `CP_BAUDRATE`, `CP_REQUEST_CANIDENTIFIER`,
  `CP_RESPONSE_CANIDENTIFIER`, `CP_GLOBAL_REQUEST_CANIDENTIFIER`, `CP_STMIN_SUG`, `CP_BLOCKSIZE_SUG`.
- Diogenes подключается только к интерфейсам «HSCAN»; протокол блока определяется по имени профиля
  (`_KW2C3PE_` = KWP2000 на CAN, иначе UDS).
- **Способ найти блоки на CAN без CBF** (OpenVehicleDiag diag_scanner.rs): на каждый ID 0x000–0x7FF отправить
  фальшивый первый кадр ISO-TP `10 10 00 00 00 00 00 00`; блок, говорящий ISO-TP, ответит Flow Control на
  своём ID ответа. Затем на найденных парах проверить `10 92` (KWP) или UDS. Это сам по себе не запрос сервиса,
  но шлёт кадры на все ID — **делать только с адаптером, который умеет свой CAN ID (не наш клон), и после
  обсуждения рисков.**
- CAN-сообщения EGS52 на шине силового агрегата W203/W211 (ultimate-nag52 lib/egs52_ecus): MS_308, MS_210/212/
  268/2F3/312/608 (двигатель), GS_218/338/418 (АКПП), BS_200/208/270/300/328 (ESP), EZS_240, KOMBI_408/412,
  EWM_230 (селектор), ZGW_248/24C (шлюз). Для W639 не проверено; на OBD 6/14 W639 этих кадров, скорее всего,
  нет (там диагностический CAN за шлюзом EZS, см. 07).

## 5. mercedes-hacking-docs (rnd-ash) — шлюз OBD и «пробуждение»

https://github.com/rnd-ash/mercedes-hacking-docs (главы 1, 3, 4):
- OBD у Mercedes отфильтрован шлюзом (EZS/EIS или SAM): читать можно, но в шины пропускаются **только
  диагностические CAN ID**; обычные ID с OBD отбрасываются.
- Перед диагностикой Xentry шлёт «пакет пробуждения» — первый кадр сессии:
  W169/W203/W209/W211/W215/W219/W245 — ID `0x001C`, данные `02 10 92 00 00 00 00 00`;
  W164/W240/W251 — `0x04E4`; W216/W221 — `0x0692`. **W639 в таблице нет.** На W203 после этого
  Xentry ставит фильтр приёма `0x05FF`, ответ `0x04E0` (вероятно, адреса шлюза), 500 кбит/с.
  Это `10 92` (расширенная сессия) — по нашим правилам без согласия не отправлять.
- Сети: M-CAN (силовой агрегат, high-speed), I-CAN (салон, low-speed), D-CAN (диагностика), MOST (мультимедиа).
- Автор: «Mercedes не использует стандартные ID 0x7DF–0x7E7» — для W639 неверно (наша EGS на 0x7E1/0x7E9).
- Тайминги K-line init: быстрый — 25 мс низкий + 25 мс высокий; 5-бод — 200/400/400/400/400/200 мс.
- Пример Flow Control `30 08 28`: можно слать, блоки по 8 кадров, пауза 40 мс.
